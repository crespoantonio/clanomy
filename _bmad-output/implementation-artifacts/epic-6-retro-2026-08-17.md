## 2. Retrospective Discussion Summary

### What Went Well
* **Interactive Setup & Discovery:** Designed a clean multi-step connection flow (`/notion`, `/notion connect <token>`, `/notion setdb <id>`) that searches and displays available user databases dynamically.
* **Adaptive Schema Binding:** Built property mapping in [notion_service.py](file:///c:/Users/cresp/Documents/Projectos/FamFin-AI/src/services/notion_service.py) that automatically matches concept, amount, category, date, and user attribution to any user-defined database layout.
* **Tenacity Error Resilience:** Integrated tenacity retries with exponential backoff and jitter, distinguishing between transient (retryable) and permanent (fail-fast) failures.
* **Data Integrity Tracking:** Extended the `Transaction` schema to track `notion_page_id` and `notion_synced_at`, enabling catch-up worker queries via `/notion sync`.
* **Previous Retro Follow-through:** Fully delivered all 3 commitments from Epic 5's action plan.

### Challenges and Lessons Learned
* **Background Database Session Isolation:** Background task workers running concurrently with request event loops require dedicated database sessions to prevent race conditions or session leakage.
* **Testing Retry Backoffs:** Mocks for tenacity required custom side-effects to test timeouts and 429 rate limit triggers without artificially slowing down test execution times.
* **FastAPI Event Loop Footprint:** Because background task execution is in-process, CPU-bound tasks or concurrent blocking I/O could trigger thread starvation. A distributed queue (e.g. Celery) should be considered for scale.
