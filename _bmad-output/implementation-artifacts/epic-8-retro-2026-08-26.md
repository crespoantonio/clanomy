## 2. Retrospective Discussion & White-Box Discoveries

### What Went Well
* **End-to-End Dual-Intent Flow:** Users can log both voice notes and text messages for expenses and earnings seamlessly. The orchestrator accurately extracts amounts, concepts, and categories while giving upbeat income confirmations with instant monthly savings rate snapshots.
* **Conversational ASK Intelligence:** The query engine understands complex cash flow questions (*"How much did we make this month?"*, *"What's our net balance?"*, *"Are we spending more than we earn?"*) and responds empathetically based on whether the household is in surplus or deficit.
* **Notion & Export Parity:** Notion mirroring and GDPR exports were updated to include transaction `Type` without breaking backward compatibility or failing on databases without a pre-configured `Type` column.

### Challenges & Architectural Discoveries
* **SQLModel Model vs. DB Column Alignment:** Harmonized the `type` column mapping so that both `Transaction.type` ORM queries and instance property accesses (`tx.type`, `tx.tx_type`) work consistently across SQLite and PostgreSQL.
* **Defensive Intent Ambiguity:** Confirmed that ambiguous natural language input (e.g. *"50 for scooter"*) defaults safely to `expense` to prevent false positive earnings from skewing household budgets.
* **Zero-Income & Deficit Guardrails:** Protected mathematical calculations from division-by-zero errors when total income is zero, transitioning smoothly to deficit alerts.
* **Multi-Currency Segregation:** Multi-currency transactions (e.g. USD vs EUR) are segregated into dedicated buckets so cash flow totals are never mixed across differing currencies without explicit conversion.

## 3. Key Discussion Topics with Project Lead

### A. Conversational Corrections / Editing
* **Discussion:** Explored user capability to issue conversational correction commands (e.g. *"change the latest to income and not expenses"*).
* **Finding:** While not in current Epic 8 scope, this represents a significant UX improvement for instant error recovery.
* **Agreement:** Captured as a high-priority action item / roadmap feature candidate.

### B. Database Stored Procedures vs. Zero-Knowledge Privacy
* **Discussion:** Evaluated moving decryption and aggregation logic into database stored procedures to reduce service-side compute.
* **Finding:** Clanomy's zero-knowledge security model requires secret encryption keys to reside solely in application memory. Stored procedures would expose raw keys to the database host.
* **Optimization Strategy:** Retain application-level encryption for privacy, supported by indexed SQL filtering (`family_id`, `timestamp`, `type`) and a planned encrypted monthly summary cache table for extreme transaction volumes.
